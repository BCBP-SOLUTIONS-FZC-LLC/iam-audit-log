# Enterprise Platform Observability Standard — iam-audit-log

This service implements the **Enterprise Platform Observability Standard**, which defines a consistent three-tier observability taxonomy across all platform domains (IAM, Workflow, Billing, Tender Management, Notifications, and future services). The standard is enforced mechanically by platform-gincommon (see `platform-gincommon/docs/observability/`) and by the CI gates listed below.

**Standard compliance summary:** all naming rules, suffix rules, label governance, CI validation checks and backward compatibility requirements are satisfied. Six metrics (five Tier 1, one Tier 2) are `proposed` pending registry ratification — their formal submissions are in [`governance-submissions.md`](governance-submissions.md).

This page covers what is specific to iam-audit-log. The service-level design is LLD §11 (`docs/lld/iam-lld-audit-log-service.md`) and BUILD_PLAN gaps 43 and 46.

## Platform libraries

| Library | Version | Emits here | Wiring |
|---|---|---|---|
| platform-gincommon/v2 | v2.1.0 | `platform_http_*`, `platform_build_info`, `platform_library_info{library="platform-gincommon"}`. It also owns the registry and `metricslint` | `gincommon.ObservabilityMiddlewares(cfg)` in `cmd/server/main.go`. `/metrics` is served by `gincommon.MetricsHandler()` (through `outbound/telemetry`) on `METRICS_PORT` |
| platform-events/v2 | v2.2.1 | `platform_messages_{received,processed,failed}_total`, `platform_retry_total`, `platform_event_propagation_seconds`, `platform_messages_in_flight`, `platform_message_processing_duration_seconds`, `platform_dependency_request_seconds` (`sqs`, `codec`). It adopts the service-built `platform_dlq_messages_total`, `platform_duplicate_messages_total`, `platform_queue_depth` and `platform_dlq_depth`. Its publisher and outbox collectors are registered but stay at zero (AL-INV-10) | `events.InitMetrics(events.MetricsIdentityFromLabels(gincommon.MetricsConstLabels()), gincommon.MetricsRegisterer())` in `initLibraryMetrics` (`cmd/server`) |
| platform-pgcommon/v2 | v2.0.2 | `platform_db_*`, with the pool label set per binary (the `audit_app` pool in `cmd/server`, the `audit_reconciler` pool in `cmd/reconciler`) | `pgmetrics.InitWithIdentity(pgmetrics.IdentityFromLabels(...), gincommon.MetricsRegisterer())`, before `pgcommon.NewPool` |

All three register on `gincommon.MetricsRegisterer()`, so one scrape serves every collector. Startup order in `cmd/server`:

1. `InitTracingWithConfig` (same identity).
2. `ObservabilityMiddlewares` fixes the identity.
3. `metrics.Register` builds this service's collectors, including the registry-shared ones platform-events later adopts.
4. `events.InitMetrics`.
5. `pgmetrics.InitWithIdentity`.
6. The pools are created.

`metrics.Register` returns an error until gincommon's identity exists. `TestMetrics_LibrariesShareServiceCollectors` pins the order: a `RegistrationWarning` from platform-events would mean the library's recordings into a shared metric are lost. The reconciler follows the same order, but initialises pgcommon's metrics only (it uses no platform-events API).

## Identity

| Label | Value | Source |
|---|---|---|
| `domain` | `iam` | `config.ObservabilityDomain` → `gincommon.Config.Domain` (Helm also sets `OBSERVABILITY_DOMAIN=iam`) |
| `service` | `iam-audit-log` | `SERVICE_NAME`, default `iam-audit-log`, in **both** binaries (`cfg.ServiceName` in `cmd/server`; `cfg.MetricsServiceName` in `cmd/reconciler`) |
| `environment` | `local`, `dev`, `test`, `staging` or `prod` | `APP_ENV` (default `dev`), validated by `config.LoadServer` / `LoadReconciler` against `config.Environments`, and passed explicitly to metrics and tracing so they cannot disagree |
| `version` | build version | `-X main.buildVersion` / `BUILD_VERSION`; only on `platform_build_info` |

The reconciler shares the server's metrics identity, because gincommon's Tier 3 constructors require `iam_audit_log_*` series to carry `service="iam-audit-log"`. Its traces keep `service.name=iam-audit-log-reconciler` (`cfg.ServiceName`, passed to `InitTracingWithConfig`), and each run is one `reconciler.<job>` span. The reconciler CronJobs are **not scraped**, and nothing pushes their counters. Every archival, redaction and queue signal an alert depends on is a gauge that `cmd/server` publishes from database and SQS state (`OpsMonitor`, every `OPS_STATS_INTERVAL`, decision D-21). A failed run pages through `kube_job_status_failed` instead (RB-9).

One process has one identity: gincommon rejects a second one (`metrics.ErrIdentityMismatch`). The tests that need `APP_ENV=prod` therefore run in a child process (`fixtures.InOwnProcess`).

## Tiers in this service

| Tier | Namespace | Built by | Count |
|---|---|---|---|
| 1 — platform-shared | `platform_*` | The libraries. This service builds five of them from the registry, `gincommon.NewSharedCounterVec` / `NewSharedGaugeVec` / `NewSharedHistogramVec`: the ones it records into itself, which platform-events adopts. They are `platform_dlq_messages_total`, `platform_duplicate_messages_total`, `platform_dependency_request_seconds`, `platform_queue_depth` and `platform_dlq_depth` | see [inventory](metric-registry.md) |
| 2 — IAM domain-shared | `iam_*` | `gincommon.NewSharedCounterVec` from the registry: `iam_rls_violations_total` | 1 |
| 3 — service-specific | `iam_audit_log_*` | `gincommon.NewCounterVec` / `NewCounter` / `NewGauge` / `NewHistogramVec`, which validate the `iam_audit_log_` prefix, suffixes and prohibited labels and inject the identity. The one exception is `iam_audit_log_catalog_plans_stale_seconds`, a `GaugeFunc` that gincommon has no constructor for, registered on gincommon's registerer with its const labels | 18 |

Label **values** stay inside the registry vocabulary (`deploy/monitoring/metric-registry.yaml` `label_vocabulary`; constants in `internal/core/port/metrics.go`):

- `iam_rls_violations_total{violation_type}` is one of `cross_tenant_access` or `missing_or_invalid_guc`, the values `rls_check_tenant()` writes. `Ops.AddRLSViolations` maps anything else to `other`. The registry's fourth value, `missing_primary_email`, is written only by iam-user-profile.
- `event_type` is bounded by `domain.EventTypeLabel`: a type known to the taxonomy for its topic is kept, and anything else becomes `unknown`.
- `source_service` and `plan_code` are bounded by `label()` in `metrics/service.go`: a lowercase slug of at most 64 characters, else `other`; an empty value is `none`.
- `platform_dependency_request_seconds{dependency}` is one of `catalog-admin` or `s3` (service-recorded), or `sqs` or `codec` (platform-events). `{outcome}` is `success` or `error`.

No metric carries a high-cardinality label (`tenant_id`, `user_id`, `event_id`, `subject_id`, ...). `metric-registry.yaml` lists the forbidden keys, and gincommon rejects them at construction.

### Who counts what (no double counting)

- **`platform_dlq_messages_total`** is counted once per message, by exactly one owner:
  - `reason="max_receive_count"`: this service's dead-letter handler, on the delivery past `SQS_MAX_RECEIVE_COUNT − 1`. It returns an error, so the SQS redrive moves the message and platform-events does not count it again.
  - `reason="malformed"` / `"decode_error"`: platform-events, when `WithDLQForwarding` forwards the message to its queue's DLQ (decision D-22).

  `platform_dlq_depth` then shows the message per queue.
- **`platform_duplicate_messages_total`** is counted by the service, since platform-events' inbox is not used (dedup is the `processed_events` ledger, AL-INV-4). The Tier 3 `iam_audit_log_duplicate_events_total{consumer}` counts the same bus hits and also direct-write replays, which are not messages.
- **`platform_messages_{received,processed,failed}_total`, `platform_retry_total` and `platform_event_propagation_seconds`** are counted by the platform-events consumer. The service never records them.
- **`platform_dependency_request_seconds`** is recorded by the service for `catalog-admin` (the CAT-I2 poll) and `s3` (archive reads and writes), and by platform-events for `sqs` and `codec`.
- **`platform_queue_depth` / `platform_dlq_depth`** are set by `OpsMonitor` in `cmd/server` from SQS `ApproximateNumberOfMessages`. platform-events' own queue-depth sampling is not enabled.
- **`iam_rls_violations_total`** is fed from `rls_violation_log` through `audit_rls_violation_counts()` (migration `000010`). It advances a watermark `FOR UPDATE`, so with several replicas each violation is counted exactly once fleet-wide.

## Proposed metrics in live rules

Several `platform_*` successors this service depends on are `proposed` in the registry, as is `iam_rls_violations_total`. The platform libraries removed every pre-standard name (see [migration.md](migration.md)), so the live rules have to read them. `metrics-registry-lint.sh` therefore requires every live use to be **marked** rather than forbidden:

- an alert gets the label `metric_status: proposed`;
- a recording rule gets a `# metric_status: proposed` comment;
- a dashboard panel gets `(Proposed)` in its title;
- an adapter rule gets the comment, and the HPA gets the `observability.platform/metric-status: proposed` annotation.

When governance ratifies a metric, flip its status to `StatusCanonical` in `registry.go` and in `metric-registry.yaml` and drop the markers. `TestRegistryLedger_MatchesPlatformRegistry` fails until both agree with the registry.

## Tier classification rationale

The standard's three-step decision tree was applied to every metric this service emits:

**Step 1 — Cross-domain? → `platform_*`**

| Metric | Decision |
|---|---|
| `platform_dlq_messages_total` | Messages reaching the DLQ threshold: applies identically to any SQS-consuming service in any domain. ✅ Canonical |
| `platform_duplicate_messages_total` | Dedup hits on redelivered messages: universal at-least-once pattern across all event-driven services. ✅ Proposed (submission: `governance-submissions.md`) |
| `platform_dependency_request_seconds` | Outbound call latency to any named dependency: meaningful to Billing (Stripe), Workflow (external APIs), Tender, etc. ✅ Proposed |
| `platform_queue_depth` | SQS queue depth: used as an HPA signal by every queue-based service. ✅ Proposed |
| `platform_dlq_depth` | DLQ depth: compliance/health signal relevant to any SQS consumer. ✅ Proposed |

All five fail step 1 → NO for Tier 3 options. All five pass step 1 → YES for Tier 1.

**Step 2 — IAM-domain shared? → `iam_*`**

| Metric | Decision |
|---|---|
| `iam_rls_violations_total` | RLS violation detection via the `app.tenant_id` GUC pattern: used by iam-org-membership and iam-user-profile with identical semantics; Billing and Workflow do not use this RLS model. ✅ Proposed (submission: `governance-submissions.md`) |

**Step 3 — Service-specific → `iam_audit_log_*`**

All 18 Tier 3 metrics are specific to this service's behavior (ingest, archival, redaction, plan-window, export, CAT-I2 poller, RLS gauges). No other service has an `audit_events` append-only partition table, a `processed_events` dedup ledger, or a CAT-I2 plan-window projection.

The Tier 3 service token is `audit_log`, derived from the service name `iam-audit-log`. `check-metric-naming.sh` and `metric-lint.yaml` (`no_service_name_in_shared_names: true`) enforce that this token never appears in `platform_*` or `iam_*` names.

## Adding a metric

1. Decide the tier with the standard's decision tree. A new `platform_*` or `iam_*` metric is a registry PR to platform-gincommon, never a local definition (standard rules 11–12). Default to Tier 3.
2. Tier 3: in `buildCollectors` (`business.go`), use gincommon's constructor (`NewCounterVec`, `NewCounter`, `NewGauge`, `NewHistogramVec`) and name it `iam_audit_log_<name>`:
   - Suffix: `_total` for a counter, `_seconds` for a histogram, none for a gauge.
   - Labels: snake_case and bounded. Never a tenant, user, request or event id.
   - gincommon rejects anything else at startup, and `check-metric-naming.sh` fails on `prometheus.New*` other than a `GaugeFunc`.
   - Add the recording method on the matching adapter type (`service.go`, `archive.go`, ...) and its port.
3. Record one sample in `gatherAll` (`test/unit/metrics_registry_test.go`) so the scrape `metricslint` validates includes it.
4. Add it to `deploy/monitoring/metric-registry.yaml` and as an LLD §11 row (`TestMetrics_LLDTier3Registered`).
5. Run `make metrics-inventory` and commit the regenerated [`metric-registry.md`](metric-registry.md).
6. If it backs an alert, run `make prometheusrule` and add the alert to [`runbooks.md`](runbooks.md).

## CI enforcement

All of these run in `make ci` and in `Validate / Quality` (`.github/workflows/validate-quality.yml`):

| Check | What it enforces |
|---|---|
| `check-metric-naming.sh` | Every collector in `business.go` uses the right constructor for its tier: `NewShared*Vec` for registry names, gincommon's Tier 3 constructors for `iam_audit_log_*`. It also checks suffixes and the `iam_audit_log_` prefix |
| `check-observability-confinement.sh` | Logs, metrics and traces go through gincommon only. Nothing imports OpenTelemetry or promhttp, and nothing registers outside `gincommon.MetricsRegisterer()` |
| `metrics-registry-lint.sh` | Every live alert, recording rule, dashboard panel and adapter rule that reads a proposed metric is marked |
| `metricslint.sh` (`make metrics-lint`) | It runs three checks:<br>• platform-gincommon's `metricslint check` on a real scrape (registry compliance, label vocabulary, cardinality), with `-allow-proposed-owner platform-gincommon,platform-events,platform-pgcommon`<br>• `metricslint refs` on `deploy/` and the operator docs: no removed or unregistered names in alerts, dashboards or runbooks<br>• the inventory in [`metric-registry.md`](metric-registry.md) matches the code |
| `test/unit/metrics_registry_test.go` | Every check in `metric-lint.yaml`. The `registry.go` ledger agrees with the central registry, Tier 2 included. The full scrape validates with no accepted findings. platform-events adopts the shared collectors |
| `test/unit/observability_contract_test.go` | LLD §11 matches the registered metrics. Every rule, SLO, dashboard and adapter expression reads a known metric. The Helm `PrometheusRule` equals the three rule files |

`metricslint refs` scans directories only for rule and dashboard extensions (`.yml`, `.json`, ...), so `metricslint.sh` names the operator Markdown files explicitly. `migration.md` is excluded on purpose, since it lists the removed names.

`metricslint check -strict` would fail today on every `proposed` entry without an allowed owner, which includes `iam_rls_violations_total` (no IAM owner yet).

## SLOs

Recording rules and multi-window burn-rate alerts live in `deploy/monitoring/slo-rules.yml`. Fast burn means the 1 h and 5 m ratios are above 14.4× the budget (critical); slow burn means the 6 h and 30 m ratios are above 6× (warning).

| SLO | SLI (recording rule) | Objective | Alerts |
|---|---|---|---|
| Ingest lag (HLD §3.4) | `slo:audit_log_ingest_lag:error_ratio_{5m,30m,1h,6h}`: share of `iam_audit_log_ingest_lag_seconds` above `le="0.05"` (`recorded_at − occurred_at`) | 99% ≤ 50 ms | `IAMAuditLogIngestLagSLOFastBurn`, `IAMAuditLogIngestLagSLOSlowBurn` |
| Event propagation | `slo:audit_log_propagation:error_ratio_*`: share of `platform_event_propagation_seconds` above `le="5"` (envelope time to first receipt) | 99% ≤ 5 s | `IAMAuditLogPropagationSLOFastBurn`, `IAMAuditLogPropagationSLOSlowBurn` (proposed) |
| API availability | `slo:audit_log_availability:error_ratio_*`: `status_class="5xx"` share of `platform_http_requests_total` | 99% non-5xx | `IAMAuditLogAvailabilitySLOFastBurn`, `IAMAuditLogAvailabilitySLOSlowBurn` (proposed) |
| DLQ depth | `slo:audit_log_dlq_depth:ok`: `platform_dlq_depth == 0` | always, no budget | `IAMAuditLogDLQNotEmpty` (any DLQ'd audit event is a compliance incident) |

Every SLI keeps `domain`, `service` and `environment`.

## HPA

`deploy/monitoring/prometheus-adapter-rule.yaml` exposes two optional HPA inputs; CPU and memory remain the primary signals. Both read proposed metrics, so they carry the markers above.

- `platform_http_requests_per_second` (pods, from `platform_http_requests_total`), used by `autoscaling.targetRPSPerReplica`.
- `platform_queue_depth_audit_log` (external: the backlog summed across the 11 inbound queues), used by `autoscaling.targetQueueDepthPerReplica`.
